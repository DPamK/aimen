## 工作流程

### 阶段0: 对齐consituation

在任务开始之前，先检查根目录下是否有 `consituation.md` 文档，如果没有，拒绝执行后续步骤。

### 阶段一：理解需求

在开始任何编码工作之前，先仔细阅读需求，明确以下几点：

- 功能边界：这个功能要做什么、不做什么
- 输入与输出：函数签名、接口路径、参数格式、返回值格式
- 异常场景：哪些输入是非法的，应当如何处理

如有不明确之处，拒绝执行接下来的步骤，直接告知用户需要补充的信息。

### 阶段二：编写验收脚本（Acceptance Test）

**在写任何功能代码之前**，先在 `verify/` 目录下创建验收脚本。

验收脚本规则：

- 文件命名：`verify/verify_<功能名称>.py`
- 验收方式：直接调用功能函数，或通过 HTTP 请求调用接口（根据需求类型选择）
- **必须包含恰好 3 个测试样例**，覆盖：
  1. **正常场景**：典型的合法输入，验证核心功能正确性
  2. **边界场景**：边界值、空值、最大值、最小值等极端合法输入
  3. **异常场景**：非法输入、错误参数、越权访问等，验证错误处理是否符合预期
- 每个测试样例用函数封装，命名为 `test_case_1_normal`、`test_case_2_boundary`、`test_case_3_exception`
- 脚本末尾提供 `main()` 函数统一运行所有样例，并打印清晰的通过/失败状态
- 验收脚本此时运行会失败（因为功能尚未实现），这是正常的
验收脚本模板：

```python
"""
验收脚本：<功能名称>
需求描述：<简要描述>
"""

def test_case_1_normal():
    """测试样例1：正常场景 - <描述>"""
    # 调用功能或接口
    # 断言结果符合预期
    pass

def test_case_2_boundary():
    """测试样例2：边界场景 - <描述>"""
    pass

def test_case_3_exception():
    """测试样例3：异常场景 - <描述>"""
    pass

def main():
    cases = [
        ("正常场景", test_case_1_normal),
        ("边界场景", test_case_2_boundary),
        ("异常场景", test_case_3_exception),
    ]
    passed = 0
    for name, fn in cases:
        try:
            fn()
            print(f"[PASS] {name}")
            passed += 1
        except Exception as e:
            print(f"[FAIL] {name}: {e}")
    print(f"\n结果：{passed}/{len(cases)} 通过")

if __name__ == "__main__":
    main()
```

### 阶段三：编写单元测试并实现功能

无论功能涉及一个函数还是多个函数/类，**都必须遵循 TDD 原则**，先写单测，再写实现。

> 注意：单测与验收脚本是两种不同的测试：
> - **单测**（`tests/`）：面向函数/类的内部实现，白盒测试，粒度细，使用 `pytest` 框架运行
> - **验收脚本**（`verify/`）：面向最终功能的黑盒验证，模拟真实调用，独立运行，两者不可混用或替代

具体步骤：

1. **分析设计**：列出需要实现的所有函数/类及其职责，明确模块划分
2. **先写单测**：在 `tests/` 目录下为每个模块创建单测文件
   - 命名规则：`tests/test_<模块名>.py` 或者 `tests/xxx/test_<模块名>.py`
   - 针对每个函数/方法编写独立的单元测试，覆盖：正常路径、边界条件、异常处理
   - 此时运行单测应当失败（红），这是预期的
3. **再写实现**：在 `src/` 目录下创建对应的功能模块
   - 命名规则：`src/<模块名>.py` 或者 `src/xxx/<模块名>.py`
   - 只实现满足单测所需的最小代码，不过度设计
4. **运行单测**：确保所有单测通过（绿）后再继续
5. **重构优化**：在单测保护下对代码进行必要的重构，不破坏已有测试

单测执行方式：

```bash
python -m pytest tests/ -v
```

在单测全部通过的基础上，整合所有模块，完成完整的功能实现：

- 功能代码统一放在 `src/` 目录下
- 保持代码结构清晰，模块职责单一
- 添加必要的类型注解和文档字符串

### 阶段五：运行验收脚本

功能开发完成后，**必须**执行验收脚本进行验收：

```bash
python verify/verify_<功能名称>.py
```

- 若 3 个样例全部通过，进入下一阶段
- 若有样例失败，分析原因并修复功能代码，直至 3 个样例全部通过
- **禁止修改验收脚本来强行通过，只能修改功能实现代码**

验收通过后，检查并删除开发过程中产生的所有临时文件：

- ✅ 保留：`src/` 下的功能代码
- ✅ 保留：`tests/` 下的单测文件

## 核心原则

1. **测试先行**：任何功能代码必须在对应测试存在之后才能编写，严禁跳过
2. **验收驱动**：验收脚本是最终交付标准，不可为了通过验收而篡改脚本
3. **最小实现**：只写满足测试所需的代码，不过度设计
4. **持续验证**：每完成一个模块立即运行对应测试，不积累未验证的代码
5. **整洁交付**：最终交付物中不包含任何临时文件或调试代码
6. **文档完整**：每个需求必须有对应文档，有则补充，无则创建，严禁遗漏或重复
